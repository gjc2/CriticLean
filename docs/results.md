# 如何阅读实验结果

本项目只有一个模型、一个正式协议。阅读结果时，分别看公开标签、模型原始判断及技术记录，不存在第二个程序语义裁决。

## 一条样本经历什么

```text
作者原始 user 消息
    ↓ 每题一次 DeepSeek 请求
原始可见回复：reasons + is_assistant_correct
    ↓ 提取唯一显式标签；不检查理由
Correct / Incorrect，或明确技术失败
    ↓ 与本地公开参考标签比较
混淆矩阵、ACC、失败数和用量
```

例：模型回答 `"is_assistant_correct": "Incorrect"`，程序就记录“不对应”。理由中即使存在需要进一步确认的问题，程序也不据此改成未知；引文是不是逐字匹配不参与标签处理。程序只有在请求失败、回复截断／不完整或无法唯一提取标签等情况下记录技术失败。理由中存在非法 JSON 转义时，可从原始文本恢复唯一显式标签；不能从理由的意思猜出标签。

## 三类记录分别表示什么

| 记录 | 来源 | 用途 |
| --- | --- | --- |
| `gold.jsonl` 中的参考标签 | 作者发布的 `tag` | 评分参照，模型不可见 |
| 原始回复中的 `is_assistant_correct` | DeepSeek | 实验要测量的判断 |
| 预测和 traces 中的状态 | 调用及标签解析过程 | 区分有效判断与技术失败 |

`Correct` 在内部存成 `supported`，`Incorrect` 存成 `contradicted`。`unknown` 只代表技术上没有取得可用标签，不能解释为模型主动保守弃权。公开标签若有争议，另行记录，不在本次基准分数中私自改标。

## 原始标签与评测范围

正式 500 条中：

| 原始标签 | 数量 | 评分二分类 |
| --- | ---: | --- |
| `compile_right_is_right` | 250 | 正类：对应 |
| `compile_right_is_false` | 200 | 负类：不对应 |
| `compile_false` | 50 | 负类：不对应 |

`metrics.json` 分别给出：

- `overall`：全部 500 条，是主结果。
- `author_compile_passing_subset`：作者标为编译通过的 450 条，聚焦通过编译后的对应检测。
- `per_public_tag`：按上述三个原始标签分别统计。

“作者标为编译通过”不是本项目新跑编译的结果。对于 5 条连接测试，以上各块只覆盖所选样本；不能把其 ACC 写成 500 条基准成绩。

## 混淆矩阵和 ACC

以“对应”为正类：

| 公开标签 | 模型 `Correct` | 模型 `Incorrect` | 技术失败 |
| --- | --- | --- | --- |
| 对应 | TP，正确接受 | FN，错误拒绝 | `unknown_positive` |
| 不对应 | FP，错误接受 | TN，正确拒绝 | `unknown_negative` |

主要字段：

| 字段 | 含义 |
| --- | --- |
| `counts.true_support` | TP |
| `counts.false_support` | FP |
| `counts.true_rejection` | TN |
| `counts.false_rejection` | FN |
| `unknown` | 没有有效模型标签的题数 |
| `classification_metrics.ACC` | `(TP + TN) / N` |
| `classification_metrics.TPR` | `TP / N_positive` |
| `classification_metrics.FNR` | `FN / N_positive` |
| `classification_metrics.TNR` | `TN / N_negative` |
| `classification_metrics.FPR` | `FP / N_negative` |
| `coverage` | `(TP + FP + TN + FN) / N` |

每个比例对象包含 `numerator`、`denominator` 和 `value`。`value` 是 0 至 1 的小数，不是已经乘 100 的百分数；分母为零时为 `null`，不是零。

`N` 包含所有有公开标签的题目，包括技术失败。因此有失败时，`TPR + FNR` 或 `TNR + FPR` 可能小于 1；余下部分为相应类别的技术失败率。如果另行只对有效标签计算正确率，必须明确标注，不能取代全量 ACC。

主结果字段为：

```text
overall.classification_metrics.ACC.value
```

对论文历史结果的比较应优先列出 ACC、原始混淆矩阵及失败数。论文表格的 FPR/FNR 命名与标准定义存在差异，本项目不猜测作者私有 scorer 的实现，也不把这里标准定义下的同名字段直接视为完全相同口径。

## 在哪里查看 Prompt 与回复

| 文件 | 内容 |
| --- | --- |
| 准备目录的 `author-prompts.jsonl` | 对照公开输入的原始单条消息 |
| 运行目录的 `author-messages.json` | 本次选中样本实际采用的提示快照 |
| 运行目录的 `traces/*.json` | 单次请求内容、原始可见回复、状态及 API 用量 |
| 运行目录的 `predictions.jsonl` | 标签提取结果和简要理由 |
| 运行目录的 `report.md` | 逐题概览 |
| 运行目录的 `manifest.json` | 运行状态、哈希、版本和累计用量的可读镜像 |
| 运行目录的 `checkpoint.json` | 权威原子检查点，须与整个目录一并保留，勿手工修改 |
| 评分目录的 `summary.md` | 总体指标和失败概览 |
| 评分目录的 `per-case.csv` | 逐题参考标签、模型标签与一致性 |
| 评分目录的 `metrics.json` | 主指标与各子集指标 |
| 评分目录的 `diagnostics.jsonl` | 评分时发现的缺失／格式／绑定问题 |

用 `case_id` 在文件间定位同一题，检查原文与 Lean 的 SHA-256 是否一致。原始回复应和提取标签一起保留，而不是只保留分数。DeepSeek 可能返回思考 token 计数；这不意味着接口提供了完整内部思考文本，也不能视为已经核验了推理。

## 技术失败怎么处理

先看对应 trace 的错误和原始响应，不通过再次请求模型来“修复”原实验。常见情况如下：

| 情况 | 处理 |
| --- | --- |
| 缺少／含控制字符的密钥或输入错误，尚未派发 | 修复本地配置后运行；密钥本地校验失败不会创建输出目录 |
| API 身份、额度或网络错误 | 保留失败记录；检查服务商与网络后使用新实验目录 |
| 回复不完整或达到输出上限 | 保留截断记录；提高上限属于新运行条件 |
| 回复没有唯一显式标签 | 保留原文及解析失败，不根据理由猜标签 |
| 中断前已派发，但没有完整本地结果 | 恢复时记为中断技术失败，不自动重复付费 |
| 运行目录写入或哈希被修改 | 停止使用该目录作可复现结果，保留原件另行调查 |

`checkpoint.json` 保存权威状态，`manifest.json` 与 `predictions.jsonl` 是可读镜像。中断后先执行 `run --resume`，再执行 `evaluate`；评分会拒绝尚未完成的运行或落后镜像。`--resume` 继续同一实验，不会重新请求已完成或已派发的题目。只重跑失败题会改变样本选择与请求次数，必须单独报告，不能择优替换原全量分数。

## 本地旧版 52 条为什么没有判断

本工作区的 `deepseek-bench500-v1` 使用旧版 8192 输出预算。52 条因服务端 `max_output_tokens` 截断：49 条未形成最终回复文本，3 条只有部分最终文本，**52 条都没有出现最终显式标签**。它们不属于已经给出对／错但被程序语义否决的情况，也不属于模型主动弃权。思考 token 同样消耗输出预算，因此可能在生成最终 JSON 前用尽上限。

该旧运行正式分数 389/500＝77.8% 保持不变。0.2.1 把上限提高到官方最大 393216，取消客户端时长与响应大小限制，降低再次受旧限额影响的可能；服务端仍有硬上限，无法保证零截断或所有请求必定返回标签。新参数必须用独立目录。由旧失败状态选出的 52 条，最多只能报告为“52 条截断子集重跑”；要比较新预算的完整基准成绩，应单独跑全部 500 条。

旧运行 ID 196 的回复已有显式 `Correct`，其 `reasons` 中的非法 JSON 转义导致旧解析失败。这与上述 52 条不同。新解析兼容性可以恢复唯一显式标签，但不改写旧 run／report；离线重解析结果应单列版本、来源和口径，不能冒充重新请求的模型结果。

## 成本和运行状态

`manifest.json` 与 traces 保存接口能提供的输入、输出和思考 token 等信息。检查字段的用量来源；未返回的用量保留为未知。没有美元硬上限，没有自动核验账单，`null` 不代表免费。5 条连接测试和 500 条正式运行是独立调用，不能漏算前者费用。

0.2.1 在运行 manifest 中另外报告：

| 字段 | 含义 |
| --- | --- |
| `status: "complete"` | 全部题目已遍历，保留既有含义 |
| `valid_label_cases` | 成功取得模型显式标签的题数 |
| `technical_failure_cases` | 未得到有效标签的题数 |
| `label_status: "complete"` | 每题都取得了有效标签 |
| `label_status: "incomplete"` | 仍有题目缺少有效判断 |

如果遍历结束但标签不全，`run` 保存全部记录、报告失败数，并以 **退出码 3** 结束；因此 `run && evaluate` 会在此停止。这样不会把“循环跑完”当作“全题判断齐全”。需要统计含失败的分数时，仍可单独运行 `lean-critic evaluate --run 运行目录 --gold 对应gold.jsonl --out 新报告目录`，失败保留在分母。旧版 manifest 没有新字段，不应手工补写。

同时报告题目总数、有效标签数、技术失败数、实际派发请求数、ACC 及可获得用量。取消客户端截止时间允许等待更久，也可能长时间等待；网络或服务端仍可失败。网络失败可能发生在服务端接收请求后，本地失败不保证没有计费。

## 推荐的结果陈述

发布结果时至少填写下表，不将示例占位值当成实测：

| 项目 | 实际填写 |
| --- | --- |
| 工程版本／commit | 本次运行对应版本 |
| 数据 revision／哈希 | 见准备与运行 manifest |
| 模型与接口 | `deepseek-flash`，DeepSeek Responses API |
| 运行日期及参数 | 思考档位、输出上限（0.2.1 默认 393216）、客户端时长与响应大小限制（默认 null） |
| 样本范围 | 全部 500 条或明确子集 |
| Prompt | 公开数据 `messages`，两个模板，逐字保留 |
| 有效标签与技术失败 | 分别列数量与原因 |
| 总体 ACC | 分子／全部有标签分母，并给百分比 |
| TP / FP / TN / FN | 采用这里的正类定义 |
| 用量与费用 | 已知值、未知范围和账单来源 |
| 复现边界 | 不同模型后端，作者精确 decoder/scorer 不完全公开 |

离线测试、mock 回复或早期自写 Prompt 的 5 条结果都不能作为这套新协议的模型分数。工程在不调用真实 API 的情况下只能验证实验流程。
